## 一、项目定位

赛小蜂足球是一套面向**青少年足球赛事**的多端 SaaS 系统，采用"赛事 SaaS 获客 + 青训俱乐部经营 SaaS 转化"的双引擎模式。

核心商业链路：

```
第三方主办方使用赛事 SaaS 办赛
        ↓
俱乐部/球队免费参赛并沉淀基础档案
        ↓
机构负责人核验并认领机构
        ↓
授权复用赛事中的球队与球员资料
        ↓
进入青训经营系统试用
        ↓
付费使用日常经营能力
```

**当前阶段的关键商业事实**：赛事系统（简易模式 + 专业模式）**全部免费**，页面不得出现价格、待开通、购买入口。收费方向已确认分端推进，但支付未开放：

| 端 | 主要使用者 | 收费方向 |
|---|---|---|
| 服务号 H5 | 球员、裁判 | 蜂蜜增值、球员卡玩法（优先策划） |
| PC 后台 | 主办方 | 报名表识别、数据导入等资源服务（按额度，后续阶段） |
| 球队小程序 | 球队管理者 | 尚未确定 |

蜂蜜充值五档价格已确认（2026-10-18）：1元=10滴、5元=60滴、10元=150滴、50元=1000滴、100元=3000滴。**价格已确认 ≠ 已上线收款**，商户号与 JSAPI 权限尚待核验。

### 4.2 三层身份模型

```
User（自然人，手机号为唯一凭证）
  ├─ OrganizationMembership → Organization（机构工作空间）
  ├─ TeamMembership        → Team（球队管理关系）
  └─ TournamentStaffAccess → Tournament（赛事共享授权）
```

关键约束：
- `users.role`、`users.orgId` 是**历史兼容字段**，不得继续扩大职责。
- `orgId` 是租户数据边界；`creatorId` 只是创建人，**不能代替租户边界**。
- 球队主账号、球队子账号、赛事共享身份三者权限互不推导。
- 同一手机号在 `phone` / `phoneNumber` 命中两个账号 → 必须阻断，禁止取第一条。

## 五、核心业务流

### 5.1 赛事全流程（PC 主办方）

```
创建赛事（基础信息 → 组别 → 规程）
    ↓
报名管理（逐队专属邀请 / 赛事级认领码 / 定向组别海报）
    ↓
资格审核（球队准入 → 名单审核 → 锁名单）
    ↓
抽签（快速抽签 / 专业分组抽签 → 生成小组）
    ↓
自动排程（generateSchedule：场地 + 日内三阶段时隙）
    ↓
比赛执行（裁判端记录 / 纸质裁判表 OCR / 现场比分）
    ↓
赛果核定（updateMatch.finishOrganizerMatch 服务端结算）
    ↓
排名投影（resultCenter + dataCenter 统一积分规则）
    ↓
赛事中心公开页（H5 tournament-center）
```

关键实现细节：
- `updateMatch.finishOrganizerMatch` 在事务中核对 `expectedEventRevision`，用共享 `calculateMatchEventScore` 结算，撤销/重复 ID/点球大战不计常规比分。
- 弃赛走 `forfeitMatch`：固定弃赛方 0、对方 3，写审计，不创建进球事件。
- 排名**不由页面计算**，统一走 `dataCenter/shared/standings.mjs`。

### 5.2 球员登记（服务号 H5 为主入口）

```
微信 OAuth → 手机号验证 → 选择/新建球队
    ↓
填写资料（身份证全局命中本人档案 → "递卡确认"恢复/转队）
    ↓
上传照片 → 百度智能云抠图 → 即时构图预览
    ↓
服务端生成完整卡预览（临时预览令牌 15 分钟）
    ↓
确认构图 → 正式提交 → 事务写入 players + 流转日志
```

重要规则（2026-10-18 已发布）：
- 移出球队只解除归属关系（清 `teamId`/`teamCode`，状态保持有效），**不留归档副本**。
- 每次进出只增写 `player_team_history` 流转日志。
- 三类 `archivedReason` 的迁移残留**禁止恢复**，多档命中进人工核验。
- 通知幂等键含事件唯一标识，二次入队不被旧 outbox 吞掉。
- `TransactionBusy` 三次重试。

### 5.3 球员卡系统（最复杂的子系统）

**设计原则**：平台后台配置模板/字段/坐标/素材/卡种 → 统一模块生成完整成卡 → 各端只等比缩放整张卡，**不另画、不重排内部**。

**积分规则 v2**（`football-player-card-points/2`）：

```
基础分 B = 2 × 出场A + 首发S + floor(出场分钟M ÷ 45)
进球加分 = min(2 × 进球G, floor(B × 20%))
生涯竞技分 C = B + 进球加分
应援分 H = floor(核验应援滴数 ÷ 10)
球员卡积分 P = C + H
```

| 等级 | 积分 |
|---|---:|
| 铜卡 | 0–44 |
| 银卡 | 45–99 |
| 金卡 | ≥100 |

**高级权益**（`football-player-card-entitlements/2`）：积分 ≥100 才可更换展示照片、自由切换平台背景。首次制卡不受限。服务端校验，客户端传的 `unlocked` 一律不信。

**关键约束**：
- 球员卡积分是**派生结果**，不能由客户端或人工档案字段写成真值。
- 基础卡与限定卡并存，限定卡由服务端按独立规则发放，页面不得自行判定资格。
- 后台发布布局后，已保存卡须自动重生成并统一切换活动版本。
- 测试球队/测试球员产生的数据全部排除，即使挂在真实球队下。

### 5.4 裁判表 OCR（PC 与手机共用）

- 统一使用**百度智能云**识别，不另建腾讯 OCR 分支。
- 双栏纸表：左主队 / 右客队分别定位，标题与序号列构成边界证据。
- 行候选带 `reviewRegion`（上传图像素坐标）、`evidenceSide`，切片仅作核对证据。
- 身份匹配必须由**同队同一行的号码候选 + 姓名候选共同唯一匹配**稳定 ID，禁止最近姓名补齐。
- 识别证据带 HMAC 签名，JSON 递归规范化，字段顺序变化不影响验签。
- 换人支持 `substitutionPairing=unordered_batch`（同分钟无序批次），不推断谁替谁。
- 已锁定的电子裁判报告不能被重识别覆盖。

### 5.5 数据中心（统一统计口径）

**唯一源码**：`cloudfunctions/dataCenter/shared/`，其他云函数的 `data-center/` 是**部署副本**，只能通过 `tools/sync-data-center.mjs` 同步。

**七个指标**（`football-metrics/4`+）：

| 指标 | 单位 | 规则 |
|---|---|---|
| `starts` 首发 | 场 | 正式首发阵容的不同 matchId |
| `appearances` 出场 | 场 | 实际出场，替补未上不算 |
| `goals` 进球 | 球 | 有效事件，排除乌龙与点球大战 |
| `assists` 助攻 | 次 | 同一进球同一助攻者只计一次 |
| `yellowCards` 黄牌 | 张 | 第二黄计一黄一红 |
| `redCards` 红牌 | 张 | 有效事件版本 |
| `minutesPlayed` 出场时间 | 分钟 | 赛前保存的单场总时长 + 出场区间 |

**不可绕过的规则**：
- 球员永久 ID 不随球队变化。
- 历史归属用**比赛当时**的球队关系，不反查当前球员库。
- 未知、部分记录、无权限、失败与**真实零值必须分开表达**（`null` ≠ `0`）。
- 查询预算 20,000 条，超出返回 `DATA_SCOPE_TOO_LARGE`，**不静默截断**。
- 页面不得另写统计算法。

本地检查：
```bash
node tools/sync-data-center.mjs --check
node tools/test-data-center.mjs
node tools/check-data-governance.mjs
```

## 六、技术红线清单（编码前必读）

### 6.1 网页端零 SDK
- 禁止引入 `@cloudbase/js-sdk`。
- 登录、数据库、云函数调用全部走 `webLoginApi` 的 `dbQuery` / `callFunction` relay。
- 只有 `webLoginApi` 有 HTTP 触发器，不能假设其他函数可用。
- `web-admin-vue` 以 `/admin/` 为 base，资源路径必须兼容子目录。

### 6.2 WXML 表达式限制（小程序最大陷阱）
**只允许**：
```html
{{value}}
{{!value}}
{{value1 || value2}}
```
**禁止**：`===`、`!==`、三元表达式、`.find()`、可选链、数组索引、深层计算。

所有派生值必须在 `.js` 中预计算为 data 字段。这是 `sharedEventUi.js`、`sharedMatchUi.js`、`team-participation-view.js` 这类"预计算层"存在的原因。

### 6.3 身份与登录安全
- 禁止按固定手机号硬编码角色/权限/封禁。
- PC 微信候选识别顺序：`unionId` → `wechatOpenId` → 兼容旧 `openId`，但仍须与本次验证手机号指向同一 `User`。
- 小程序 `openId` 与 PC `wechatOpenId` **分字段保存，不互相覆盖**。
- 登录切换必须先清上一账号本地认证，再原子写入新会话。
- `bindPhone` 等已有完整服务端流程不能在前端重复验证，避免双重消费验证码。

### 6.4 租户与数据边界
- 主办方只能访问赛事所需数据，**不能**看俱乐部的学员、课程、财务。
- `users` 不属于业务清理范围，清理业务数据不能删登录账号。
- 球队资料是长期资产；参赛名单、阵容、赛果是**赛事快照**，日常修改不能覆盖已审核历史。
- 名称相同不得自动合并账号/机构/球队/球员，冲突进人工核验。

### 6.5 其他
- 云函数保持 Node.js 18 兼容，尽量减少依赖。
- 密钥、Token、验证码不得进日志或仓库。
- 删除/迁移/批量清理/生产部署必须确认精确目标并单独验证。

### 9.3 最容易踩的五个坑

1. **在 WXML 里写三元或 `===`** → 编译不报错但渲染异常，必须移到 `.js`。
2. **在页面里自己算统计** → 违反数据中心红线，必须调 `dataCenter`。
3. **直接改 `cloudfunctions/*/data-center/` 副本** → 下次 `sync-data-center` 会被覆盖，必须改 `dataCenter/shared/`。
4. **把 `null` 当 `0` 渲染** → 违反"未知与真实零值分开"规则，必须显示 `—`。
5. **以为提交就等于发布** → 云函数、小程序、静态页都是独立的发布动作，且都要读回验证。
