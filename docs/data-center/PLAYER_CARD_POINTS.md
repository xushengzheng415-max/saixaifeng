# 球员卡积分与等级规则 v2

## 平台参数配置（2026-10-16，用户确认）

平台运营后台“积分规则”配置出场分、首发分、每分所需分钟、每球加分、进球加分占基础分的上限、每分所需应援次数、银卡起点、金卡起点。规则保存草稿后须试算影响，确认发布才切换版本；未发布配置时继续使用下文V2参数。

调整规则时保留已获卡级，只允许升级。发布任务先准备稳定playerId对应的卡级保留记录，完成后事务切换规则指针。保留依据为原规则下已核定卡级、上一版本保留记录，以及受写保护且带版本的正式已制作卡级；不以姓名、手填积分或卡面颜色推断。测试身份始终排除，未核定资料不能因保留记录绕过完整度核验。

真实积分按新参数重算；换照片/背景仍以实际积分100分为门槛，不因卡级保留或金卡门槛变化自动放开。试算明确展示积分变化、升级、保留卡级、权益新增和权益重新锁定人数。试算绑定草稿修订、规则参数、操作者、数据摘要与15分钟有效期；数据变化必须重新试算。

规范参数与计算位于shared/score-rules.cjs、statistics.mjs；活动规则和保留记录读取由shared/score-rule-store.cjs统一实现，使用既有platform_settings。发布管理入口为平台鉴权后的scoreRulesRead/Save/Preview/Begin/Continue工作流，保留历史版本和原因。不改球员原始档案、比赛、应援账本或历史赛果。

以下公式和45/100门槛是默认V2，不代表后续已发布配置仍使用这些数值；实际活动版本须核对发布记录。

## 适用范围与权威来源

- 以稳定的 `players._id` 汇总该球员职业生涯，不按姓名、号码或当前球队合并。转会前后属于同一球员的正式比赛累计；球队历史贡献仍按比赛当时归属统计。
- 只计数据中心 `mode: official` 且比赛、球队、球员来源均确认为真实的有效记录。测试球队和测试球员产生的所有竞技数据都不计入正式球员生涯；测试球员即使挂在真实球队下也不例外。虚拟、测试或演示比赛即使显示“已完赛”或“已发布”也不计；来源无法核定的记录先待核定。取消、退回、冲突、现场暂定、未开赛比赛不计；数据纠正、撤销按现行事件版本重算。一场比赛对同一球员的出场和首发各最多计一次。
- 指标来自统一数据中心的 `playerTotal.metrics`：`appearances`（实际登场场次）、`starts`（正式首发场次）、`minutesPlayed`（出场分钟）、`goals`（有效进球）。替补未上场不计出场；乌龙球和点球大战进球不计进球。正式分钟使用赛前已保存且来源核定的单场总时长和出场区间，旧计时器不能覆盖最终时长；缺少可靠证据时为未知。
- 公开页面只显示有权公开的球员等级、积分及必要进度；个人完整生涯计算须具备覆盖全部相关赛事的授权。仅有当前球队或单届赛事数据时，不能标成“职业生涯总分”。

## 计分公式

设 `A` 为出场场次，`S` 为首发场次，`M` 为出场分钟，`G` 为有效进球。四项均为非负、已核定的完整生涯指标。

```text
基础分 B = 2 × A + S + floor(M ÷ 45)
进球加分 = min(2 × G, floor(B × 20%))
生涯竞技分 C = B + 进球加分
应援分 H = floor(核验应援滴数 ÷ 10)
球员卡积分 P = C + H
```

`floor` 为向下取整；分钟在生涯汇总后取整，不逐场丢弃不足 45 分钟。进球加分上限让所有位置都能凭稳定参赛升级，不让单一数据主导等级。应援仅计 confirmed 且唯一对应真实一滴扣款的记录；账本异常则总分待核定。助攻、红黄牌及人工填写的 `players.appearances/goals/points` 暂不参与；未来新增指标必须升规则版本、重跑分布与跨端验收。

| 等级 | 已核定积分 |
|---|---:|
| 铜卡 | 0–44 |
| 银卡 | 45–99 |
| 金卡 | 100 及以上 |

例如 10 场首发、每场踢满 90 分钟且无进球：`B=20+10+20=50`，为银卡；20 场同样表现为 100 分，为金卡。10 场各踢 15 分钟的替补：`B=20+0+3=23`，为铜卡。基础分 50、进球 10 粒时，进球加分为 `min(20,10)=10`，总分 60。

## 高级功能权益

权益版本 `football-player-card-entitlements/2`。以已核定的职业生涯积分 `P >= 100` 解锁，**100 分整即可使用**；旧规则授予的金卡、历史保留等级和卡面颜色本身不构成权益凭证。PC、H5、小程序读取同一服务端权益结果，不在各端单独判断。

| 操作 | 0–99 分或积分待核定 | 已核定 100 分及以上 |
|---|---|---|
| 首次制作球员卡、首次选择卡面照片 | 允许 | 允许 |
| 更换已保存球员卡的展示照片 | 锁定 | 允许，不限制更换次数 |
| 在平台提供的球员卡背景中自由切换 | 锁定，使用等级默认背景 | 允许，不限制切换次数 |

- “更换照片”特指球员卡展示照片，不影响依法更正身份资料、更新正式形象照或处理隐私删除请求；这些业务流程按原权限和审核规则执行。背景权益只覆盖平台已提供且审核通过的卡面素材；用户自行上传背景及其他玩法待后续单独定义。
- 每次保存照片或背景时，服务端重新核验本人/监护或管理权限、积分版本和权益，不接受客户端传来的等级、积分或 `unlocked` 标志。积分未知或覆盖不全时不开放新的高级操作，并保留已保存卡面；数据恢复后可重试。
- 正式数据纠错使已核定积分低于 100 时，后续更换操作重新锁定；已保存图片不自动删除，异常授予按有记录的复核流程处理。背景可以自由选择，但卡片显示的真实等级仍取服务端已授予等级，不能用金色背景冒充金卡。
- 后续新权益在本节追加名称、门槛、授权对象和服务端校验，再接入各端；不因“更多玩法”预留空入口或提前开放未定义功能。

## 完整度、卡级与升级

- `appearances`、`starts`、`minutesPlayed`、`goals` 任一指标不是 `coverage: complete`，或查询失败、范围不完整时，`P=null`、计算等级为“待核定”；不得把缺失当 0，也不得用手填档案数字补齐。确认为刚登记且没有正式比赛的球员，在全范围零场证据成立时四项均为 0，积分 0、铜卡。
- 保存 `scoreVersion`、`metricVersion`、`dataVersion`、计算时间、四项原值、基础分、进球加分、积分、计算等级和已授予等级，便于跨端回读及审计。实时统计与持久化的“已授予等级”分开：正常新增正式比赛只升级，不因缺失或暂时查询失败降级。
- 旧卡过渡：实施迁移时先留存现有已授予等级快照；新积分若更高则升级，低于旧等级则保持旧等级并标识历史保留。不可从可手改的档案场次直接伪造既有卡级。若原比赛被正式撤销、纠错或身份拆分，走有记录的复核流程，允许纠正错误授予。
- 保存过的卡面图可能仍是旧等级：服务端始终返回当前已授予等级和 `savedTier`；不一致时客户端提示“等级已更新，重新生成卡面”，不得将旧图作为当前等级的证明。客户端不得提交自选等级覆盖服务端结果。

## 统一实现与验收

1. 在共享统计模块补齐 `starts` 指标、去重与完整度；等级和积分只在数据中心共享服务计算，并由 PC、H5、小程序消费同一个版本。小程序组件、PC Vue 页面和 H5 页面不能再按 `10/20` 场或年龄推断卡级。
2. 全量重算前，按稳定球员 ID 做只读试算：统计铜银金分布、缺失率、历史卡级差异、跨队生涯覆盖、计算成本与无 ID 的公开榜单对象。无稳定 ID 的历史记录先进入质量队列，不按姓名凑生涯分。
3. 使用虚构及真实脱敏样本验收 0 场、短时间替补、首发、进球封顶、转会、重复阵容、补赛修订、撤销、缺分钟、缺首发、跨权限范围、数据读取失败及旧卡保级；另验收 99/100 分权益边界、旧金卡未满 100 分、首次选图、再次换图、背景切换、积分纠错与伪造客户端权益；对同一球员核对 PC、H5、小程序的积分、版本、等级和权益一致。
4. 部署顺序：共享统计与服务端 → 数据试算/审核 → 三端界面 → 预览回读 → 正式发布。Git 提交、知识库同步、构建和小程序上传均不等于正式环境已按新规则运行。
