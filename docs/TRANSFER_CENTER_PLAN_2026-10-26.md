## 一、定位与第一版范围

转会中心是依托赛事转会窗口的线上球队流转流程，包含正式转会、租借、自由球员签约和合同到期处理。主办方在PC赛事后台管理窗口、审核转会；球队在球队小程序浏览市场、谈判和管理合同；球员在服务号处理续约。

线上合同是用于记录所属关系与期限的象征性文本。转会费是真实人民币，平台只记录每轮报价和最终成交金额，款项由球队线下自行交付。平台不收款、不托管、不结算，不设置付款、到账或卖方确认收款作为转会生效条件。球员与新球队自行商谈薪资，平台转会流程不以薪资谈妥为前提。

第一版不做主动挂牌，不要求原队先标记“出售”“可租借”才允许别人发起意向，也不向球员显示“被球队挂牌出售”。不建设支付、薪资、经纪人、竞拍、自动身价成交或自动续约系统。

## 二、已确认玩法

### 2.1 市场与赛事窗口

- 市场谁都可以浏览；浏览权限不等于球队操作权限。仅公开可展示资料，不因此公开手机号、身份证、保险、人脸或机构经营资料。
- 第一版无需主动挂牌。市场展示球员、所属球队、位置、合同状态与允许公开的生涯资料；身价展示沿用已有成人/青少年可见规则。
- 转会依托赛事转会窗口。未参加任何赛事的球队暂不支持转会。
- 是否必须两队参加同一赛事、跨赛事审批归属、自由签约是否受窗口约束仍待决，不把建议写成已确认限制。

### 2.2 正式转会

买方选择球员并发起意向，原球队收到后进行谈判，可讨论转会方式和金额。双方同意后，进入主办方PC转会中心审核；主办方确认后完成所属球队交接，新队建立一年合同。

不设置球员同意转会的节点，不等待球员服务号回复才交接。球员薪资与两队转会费分开。转会费归原球队，平台仅留存双方最终认可的人民币金额。

“归属”指平台球队关系；球员档案仍归球员本人持有，稳定playerId、永久编号和原有历史不随球队变化。

### 2.3 三轮谈判与24小时限制

最多三轮，三轮未谈成则谈判破裂。该买方球队24小时内不得再次向同一球员发起转会申请；不将此解释为球员全平台封禁或限制其他球队报价。

建议一轮定义为“买方一份完整报价＋卖方一次接受、拒绝或还价”。第三轮结束仍无一致条件则破裂。任何金额、方式、期限的改动都生成新版本，旧同意不能批准新条件。轮次计数、提前拒绝或撤回是否触发冷却、未回复超时规则见待决项。

### 2.4 自由球员签约

自由球员已经没有所属球队，不再向原队索取同意，不产生卖方转会谈判。球队可从市场直接签约，建立一年球队关系。与在约球员的两队谈判分开，不通过“直接添加球员”绕过有效球队合同。

直接签约不设置原队审批或球员转会确认节点；是否另需赛事主办方审核、是否仅限窗口内签约，本次对话没有明确确认，保留待决。

### 2.5 租借期限与转永久

租借最短一场，最长到本赛季结束。租借保留原队关系，在约定范围内为借入队效力。原队合同期限与租借期限分别记录。

只有“整赛季租借”支持在到期前谈续租或永久转会；单场及其他短期租借不提供租借期间续租、转永久的入口。不能以短租追加一次操作的方式绕过这一限制。短租结束后的新申请是独立流程，其窗口、资格与历史限制仍须重新核验。

整赛季租借谈永久转会，继续按真实人民币金额谈判，双方同意后由主办方审核。永久转会生效后结束原队关系与租借关系，建立新队一年合同。

续租谈妥、续租所属赛季及所需审核的细节待决。建议续租用于下一赛季；当前赛季租借本身不延长到本赛季结束之后。谈判中不自动延长已约定期限。

### 2.6 一年合同与续约

新进球员和正式转会球员先按一年合同管理。合同中保留起止时间、所属球队、签约来源和状态；一年从哪个生效日计算，旧球员从何日起补合同，均不凭档案创建时间猜测。

续约由球队小程序发起，球员在服务号接受或拒绝。接受后续约；拒绝不立即解约，现合同继续到期，到期成为自由球员。不把续约放进主办方PC转会审批，不混同“转会无需球员确认”与“续约需要球员回应”。

未回复如何处理、提醒提前多少天、续约增加多久与是否允许多次发送，待决。

## 三、端口与权限

| 端口/角色 | 负责内容 | 边界 |
| --- | --- | --- |
| 球队小程序／球队管理者 | 市场、意向、谈判、自由签约、租借、合同、发起续约 | 仅操作本人获授权球队；切换球队后重新校验 |
| 球员服务号／本人或有效代管人 | 查看球队合同、接受或拒绝续约 | 不审核两队报价，不承担转会同意节点；代管回应规则待决 |
| 主办方PC／赛事管理者 | 窗口管理、转会审核、租借和交易记录 | 仅限明确赛事授权；不能借转会读取原机构课程、财务等私有资料 |
| 市场浏览者 | 查看允许公开的市场资料 | 浏览不授予报价、签约、审核或隐私读取权 |

PC入口建议放在“赛事空间 → 具体赛事 → 转会中心”，而非平台运营后台。新模块授权须由既有赛事范围体系登记，不能默认让所有赛事子账号都能审核。

## 四、业务链路与状态

### J01 正式转会

市场选择球员 → 选择操作球队和赛事 → 填写报价 → 原队回复／最多三轮 → 双方同意同一版本 → 主办方待审核 → 确认并执行交接 → 已完成。

建议状态：谈判中、已破裂、已撤回、待审核、审核未通过、待生效、已完成。审核拒绝应保留理由，不自动当作三轮破裂；退回能否重新谈、是否重置轮次待决。只有确认交接成功才显示已完成。

### J02 租借

市场选择球员 → 选择租借方式及期限 → 两队谈判 → 主办方审核 → 租借生效 → 到期返回。

单场租借需绑定具体比赛，不能只填“一场”。建议用约定比赛正式结束作为到期依据；取消、延期、无效比赛、赛果撤销时如何到期待决。比赛实际出场记录继续归属当场球队，不能归还后改成原队成绩。

### J03 整赛季租借后续

整赛季有效租借 → 到期前发起续租或永久转会谈判 → 对应审批／生效。未完成后续流程不自动续租。租借到期时原队合同也到期的，建议结束借入效力后成为自由球员，避免恢复不存在的有效合同；需确认后实施。

### J04 自由签约

市场选择自由球员 → 核验实时自由状态 → 确认签约 → 建立一年球队关系。若并发被别队签走，明确提示并刷新，不覆盖新关系、不复制球员档案。窗口和审批规则待决。

### J05 续约与自由身

球队合同页发起续约 → 服务号合同待办 → 接受或拒绝 → 球队端读回结果。拒绝后等待原合同到期 → 解除有效球队关系 → 市场显示自由球员。未回复分支不预设自动续约。

跨端消息只是提示；即使消息未送达，待办仍由服务端保留。通知能力、模板及用户可接收性在实施时核验，不能把“发送成功”当作球员已阅读或已接受。

## 五、PC与小程序界面功能

本章为逐页设计建议；延续PC01—PC03、TM01—TM05、PL01的稳定ID，补充PC04和TM06—TM10。共4个PC视图、10个球队小程序页面／表单、1个服务号衔接页；视图数不等于新增独立路由数。字段、按钮和反馈可以继续评审，Q01—Q09未定规则不能由界面默认选项代替。

### 5.1 导航与入口

PC：赛事空间 → 具体赛事 → 转会中心PC01；审核抽屉PC02、窗口配置PC03、记录PC04由此进入。球队报价不放到主办PC，也不向平台运营后台复制一套转会中心。

球队小程序：“发现 → 转会市场TM01”面向浏览；“我的转会TM08”可从市场或球队详情进入；“球队管理 → 球队合同TM05”管理合同。保留现有底部导航，不为转会新开底部主标签。续约链路从TM05、TM09、TM10到服务号PL01，不让球队代球员点击同意。

### 5.2 通用布局与状态

PC以1440×900为布局基线，复用现有300px赛事侧栏与90px顶部栏；主体随容器宽度适配，筛选、表格、分页对齐，不使用欢迎区、收益卡或大装饰图。抽屉内文滚动，底部操作固定，滚动区预留操作栏高度。

球队小程序与服务号以390×844为设计基线，并核对360与430宽。交易二级页复用原生单列白底表单、现有绿主色；发现入口保留既有品牌背景。二级页不显示底部主导航，顶部返回与标题固定，正文纵向滚动；表单底部操作栏预留安全区与键盘空间，输入项被键盘遮挡时滚动到可见区域。

颜色与尺寸：PC主色取现有#2E7D32，正文#1F2937，页面底#F6F8F7；小程序复用全局#2E7D32、正文#333333、次文#666666、白色内容面和#E0E0E0边界。建议标题18—20px、正文14—16px、间距8／12／16／24px、输入及移动触点至少44px、圆角6—10px；这些是本模块的设计取值建议，非全站重构。成功、等待、拒绝／错误同时写文字，不能只靠颜色。

金额以“¥ 1,200.00”或“1,200 元”清楚标注，最多两位小数，底层以分存储。报价与成交金额不自动公开到市场，具体范围Q09待决。参考身价与成交报价分开，不自动填写参考价或限定底价。示例仅用“示例球队甲／乙、示例球员”，不得误作真实交易。

通用反馈：首屏加载用列表骨架或明确加载状态；仅完整成功的空结果显示空状态；失败保留已知内容并给重试；无权清除当前对象数据；提交中防重复；超时先查结果；版本冲突要求读取新版本再确认。未知金额、日期和统计显示破折号／待核定，不显示0。换账号、换球队或退出后，迟到响应不能渲染。全部交互状态须由服务端返回权限与状态驱动。

文字与图标：按钮采用发起意向、接受条件、确认转会等明确动词；保留“金额线下交付”“到期后离队”等影响选择的说明，不重复写标题副文案。共享SVG用于功能控件，完整透明形象照不裁圆、不加底板；不新增每页一份图标，也不以PNG缩小代替功能图标。

### PC01 转会中心

用途：集中处理本赛事转会审核，不承担球队报价。 操作人：赛事转会管理者。形态：查询列表。

入口：赛事空间 → 具体赛事 → 左侧转会中心。

首屏与布局：固定赛事抬头：赛事、赛季、窗口状态 → 待审核／已审核／全部标签＋筛选 → 转会表格＋底部分页。

| 字段／模块 | 显示或输入 | 校验及边界 |
| --- | --- | --- |
| 赛事／赛季 | 只读上下文 | 不得凭上一赛事缓存带入 |
| 筛选 | 球员或编号、球队、正式／租借、提交日期 | 精确查询；清空恢复全部 |
| 列表 | 球员、原队→目标队、方式、金额、期限、状态、提交时间 | 待审核优先；金额仅向已获授权对象展示 |
| 分页 | 总条数、页码 | 服务端完整分页；失败不伪造0条 |

动作：

- 待审核记录：**查看审核**。打开PC02，传精确转会单ID。
- 已审核记录：**查看记录**。打开PC04，只读最终条款与日志。
- 具备窗口配置权：**窗口管理**。进入PC03。

状态反馈：

- 无待办：“暂无待审核转会”；可切换全部；不引导主办代球队报价。
- 读取失败：“转会记录未加载”；重试保留筛选，不显示空列表。
- 赛事授权失效：“无转会管理权限”；停用操作并返回赛事空间。

跳转与返回：PC02／PC04关闭回到原标签、页码与滚动位置；切换赛事清空旧选择。

页面差异：PC只显示已提交审核的最终交易及其记录；默认不展示所有球队私下谈判中的报价。列宽不足时省略非核心字段，由详情展开；1440基线不横向溢出。

功能依据：R01、R04、R08。

### PC02 转会审核

用途：核对双方已一致的条款，确认或拒绝。 操作人：赛事转会管理者。形态：审核抽屉。

入口：PC01待审核行 → 查看审核。

首屏与布局：右侧抽屉：固定标题、状态与关闭 → 球员／原队／目标队 → 最终条款 → 双方确认 → 报价历史 → 底部固定确认转会及次要拒绝。

| 字段／模块 | 显示或输入 | 校验及边界 |
| --- | --- | --- |
| 球员与双方球队 | 只读稳定编号及名称 | 同名对象按ID区分 |
| 条款 | 方式、人民币金额、合同／租借起止、比赛／赛季 | 不显示薪资、付款状态或球员同意 |
| 一致性 | 双方确认时刻及共同条款版本 | 任一版本不一致不得确认 |
| 审核意见 | 拒绝时必填文本 | 缺失定位到输入框；接受无强制长评语 |

动作：

- 待审且校验通过：**确认转会**。确认摘要后提交；服务端交接完成才显示已完成。
- 待审：**拒绝**。填写理由、确认拒绝；只保存拒绝结果，不修改球队关系。
- 提交中：**处理中**。禁用重复操作，关闭后仍可回读实际结果。

状态反馈：

- 版本变化：“条款已更新”；刷新最新内容；旧确认失效。
- 已被其他管理者处理：“已处理”；切换只读PC04，不能重复批准。
- 网络中断：“结果待核实”；先查询处理结果，再允许重试。
- 交接异常：“交接未完成”；展示任务编号及刷新；不新增人工改归属按钮。

跳转与返回：关闭返回PC01；成功后刷新待审核列表，不强制跳其他业务模块。

页面差异：建议宽720px，上下留24px，内文滚动；窄屏占满可用内容宽。二次确认只列球员、双方队、方式、金额、期限，不索取收款证明。

功能依据：R04、R08、R11。

### PC03 转会窗口

用途：维护本赛事窗口起止，明确操作时间条件。 操作人：赛事转会管理者。形态：配置表单。

入口：PC01 → 窗口管理。

首屏与布局：返回转会中心＋赛事／赛季 → 当前窗口及起止表单 → 保存按钮与最近修改信息。

| 字段／模块 | 显示或输入 | 校验及边界 |
| --- | --- | --- |
| 所属赛事 | 只读 | 跟随当前授权空间 |
| 赛季 | 选择已登记赛季 | 无有效赛季不造本赛季；定义见Q03 |
| 窗口起止 | 日期时间选择 | 统一北京时间，结束必须晚于开始 |
| 窗口状态 | 只读服务端状态 | 未开始／开放中／已关闭 |
| 修改记录 | 只读修改人、时间 | 不显示私人联系方式 |

动作：

- 具备配置权且表单有效：**保存**。保存后重读窗口及版本。
- 返回：**取消**。未保存改动提示放弃；已保存返回PC01。

状态反馈：

### TM03 转会谈判

- 列表失败：“意向未加载”；重试当前方向和筛选。
- 切换球队：“重新加载”；清除上一队记录；迟到响应不渲染。

跳转与返回：返回原市场／球队详情；从谈判返回刷新对应行，保留收到／发出标签。

页面差异：角标只显示必要待处理数；不添加交易总额、收益榜或卖人排行榜。通知缺失也能从此页找到真实待办。

功能依据：R03、R04、R08。

### TM09 合同详情

用途：看清原合同与效力关系，决定是否向球员提出续约。 操作人：球队管理者。形态：移动详情。

入口：TM05合同行；TM07签约完成；TM04查看合同。

首屏与布局：球员、合同球队、当前效力队与状态 → 起止日期／来源 → 租借信息 → 续约请求及回应记录 → 底部按合同管理权限提供发起续约。

| 字段／模块 | 显示或输入 | 校验及边界 |
| --- | --- | --- |
| 合同 | 一年或原已确认期限、起止日期、来源单号 | 合同是线上关系记录，不能在线编辑改期 |
| 租借 | 当前效力队、原合同队、起止、单场比赛或赛季 | 借入队不能续约原队合同；可回TM04谈整赛季后续 |
| 续约 | 待回应／已接受／已拒绝、拟定日期、回应时间 | 拒绝不立即离队；已接受显示新有效合同 |
| 到期 | 实际到期结果 | 未核定日期不显示自由身 |

动作：

- 本队为合同管理方且可续约：**发起续约**。进入TM10填写新条款。
- 已有有效续约待办：**查看续约**。展开原请求，避免重复生成。
- 整赛季租借信息：**查看租借**。进入TM04，仅后者承接两队续租／转永久。

状态反馈：

- 球员拒绝：“已拒绝续约”；展示现合同到期日；不提供强制续约。
- 合同已结束：“合同已到期”；不显示在原合同直接续期按钮；后续签约重新核验。
- 日期缺失：“合同日期待补齐”；停用依赖日期的续约提交，不造新起止。

跳转与返回：返回来源页；续约请求结果更新时不改变当前球队上下文；不跳主办方PC。

页面差异：“球员续约”与“两队续租”严格区分：前者服务号回应，后者球队谈判。只读正文不塞长法律条款，必要的合同全文可折叠查看。

功能依据：R05、R06、R07。

### TM10 发起续约

用途：将明确的新合同期限发给球员，等待服务号回应。 操作人：球队管理者。形态：移动表单。

入口：TM09 → 发起续约；作为表单页或全屏弹层。

首屏与布局：球员、合同球队、现合同到期日 → 拟续约起止及期限 → 简短确认摘要 → 底部发送续约；消息是否送达单独展示。

| 字段／模块 | 显示或输入 | 校验及边界 |
| --- | --- | --- |
| 原合同 | 只读到期日及合同ID | 不是球队之间租借续期 |
| 拟续约 | 新起止与新期限 | Q07未定，不擅自固定一年；日期逻辑要合法 |
| 接收人 | 球员本人或有效代管关系 | 不手填手机号改收件人；代管规则仍待确认 |
| 通知结果 | 待发送／已发送／失败 | 不与待回应／接受混成一个状态 |

动作：

- 条款完整且有权：**发送续约**。持久化请求后回TM09显示待回应；PL01形成待办。
- 发送请求失败：**重试**。保留条款；先查询同请求是否已存在。
- 请求已存在：**查看请求**。不自动再次发送或新增一份。

状态反馈：

- 通知失败但请求已保存：“续约已发起，通知未送达”；合同仍待回应；查看原请求，不重复造单。
- 合同或权限变化：“合同状态已更新”；回TM09刷新。
- 没有有效接收关系：“暂无法发送续约”；说明需核对球员关联，不绕过本人授权。

跳转与返回：成功回TM09；取消回TM09且不留请求。服务号回应由服务端状态同步，不转交球队会话或权限。

页面差异：不添加转会费、薪资、付款状态。撤回、重发间隔及替换旧请求规则未定，不提前提供可执行按钮。

功能依据：R06、R07。

### PL01 合同续约

用途：在服务号完成续约回应，仅补足球队端链路。 操作人：球员本人或有效代管人。形态：移动详情。

入口：服务号我的 → 球队合同；有效续约通知链接。

首屏与布局：球员／球队、原到期日、续约状态 → 拟续约起止及差异 → 请求时间 → 底部接受续约及次要拒绝。

| 字段／模块 | 显示或输入 | 校验及边界 |
| --- | --- | --- |
| 当前身份 | 球员或明确的有效代管对象 | 多球员显式选择；链接不能自行切换身份 |
| 条款 | 原合同到期日、新合同起止及期限 | 回应锁定同一请求版本 |
| 请求 | 请求时间和有效状态 | 失效链接保留可读结果，不允许确认旧条款 |

动作：

- 待本人回应：**接受续约**。确认本版本；成功后显示新合同。
- 待本人回应：**拒绝续约**。确认后仅拒绝请求，现合同到期再离队。
- 已处理：**只读**。展示接受／拒绝结果，不出现转会同意或重复回复。

状态反馈：

- 登录失效：“请重新登录”；验证本人后返回原请求并重新判权。
- 条款更新／请求失效：“续约请求已更新”；刷新新条款，不沿用旧确认。
- 提交超时：“结果待核实”；回读本人回应结果；不发送相反的第二次回应。

跳转与返回：返回服务号球队合同或我的；回应状态同步TM09及TM05，球队不需要拿球员链接代操作。

页面差异：此页仅作为服务号衔接，不扩展球员小程序、薪资协商或新的转会确认端。

功能依据：R06、R07、R11。

## 六、统一数据与技术边界

稳定球员身份、永久编号、历史球队贡献和已审核赛事快照不变；转会不复制档案、不改历史比赛／事件／统计，也不自动授予新队参赛资格。租借需要区分“原合同球队”与“当前效力球队”，不能让同一球员同时被两队当作当前有效在队成员。

沿用统一数据中心模块建立关系流转服务，禁止PC、小程序和H5分别写一套合同、到期或轮次算法。现有跨机构转会未开放自动执行的登记不等于本方案已上线；正式开发须补完整授权、最小资料交接和原队读权限回收。

建议记录：赛事及赛季窗口；转会单及不可变报价版本；租借协议和具体比赛；一年合同及续约请求；有效期球队关系和只增流转历史；审核及状态审计。集合名称在代码设计阶段核验现有结构后确定，不在方案阶段创建生产表。

关键约束：服务端按对象版本和当前关系检查；同一球员只允许一次有效交接；审核、到期、自由签约和租借返回使用幂等事务或可恢复执行任务；球队关系变更不得只改player.teamId。定时任务失败须补偿，不能因页面没打开就不执行到期。

网页继续走webLoginApi零SDK链路；页面读取不暴露原机构私有数据。估值仅调用统一模块，冻结转会发起时的参考快照，不重写历史、不强制按估值成交。市场谁都可看不覆盖青少年货币估值和个人隐私的既有权限。
