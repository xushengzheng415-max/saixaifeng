## 一、先说现在真实存在的 6 个风险

| # | 风险 | 证据 |
|---|---|---|
| R1 | **同一台机器只有一份工作副本**，两人同时改，谁都看不到对方的未提交改动 | 本机工作区即正式仓库，无 worktree/无独立分支隔离 |
| R2 | **双远端**：Gitee `saixiaofeng/football` + GitHub `xushengzheng415-max/saixaifeng`，谁是权威源未定义 | `AGENTS.md` 第二节同时列出两个远端 |
| R3 | **发布权没有归属**：PC 是"整包 209 个文件全量安全发布"，两个人同时发，后发的会覆盖先发的 | `AGENTS.md` 第六节 + `CURRENT_STATUS.md` 历次"安全发布 209/211 个文件" |
| R4 | **文档是共享追加日志**：`CURRENT_STATUS.md` 已 970+ 行，两人同时插入表头条目必然冲突 | 本轮新增条目即插在文件首行 |
| R5 | **云函数契约跨端**：`webLoginApi` 是所有网页端请求的唯一入口，改它的 action/返回结构会同时影响 PC / 小程序 / 服务号 | `AGENTS.md` 3.1 |
| R6 | **构建并不可复现**：本机 shell 被沙箱阻断，`npm run build` 目前跑不起来 | `SetNamedSecurityInfoW failed (Win32 5): grantWrite(E:\Documents\sxf-football)` |

## 二、R6 的解决办法（建议先做，不解决后面都免谈）

DSH 的 workspace-write 沙箱需要给工作区目录追加一条显式 DACL 授权，现在这条授权在 `E:\Documents\sxf-football` 上失败（Win32 5 = 拒绝访问），因此**任何 pwsh 命令都起不来**，构建与发布全部停摆。

按阻塞程度从低到高，三个可选做法（🔴 需要你选一个）：

1. 🔴 **把正式仓库迁到 ACL 可写的位置**（例如 `D:\Documents\sxf-football` 或用户目录下），仓库内路径不写死盘符即可；工作量集中在 `.git`、IDE 配置和 `sxf-cloud` 脚本路径。
2. 🔴 **修复 E: 目录所有权/权限**：用管理员 PowerShell 对 `E:\Documents\sxf-football` 执行 `takeown` + `icacls` 授予当前用户"完全控制"/"修改权限"，再重试。
3. 🔴 **把终端操作交给人在普通 PowerShell 里跑**：我不再需要 shell，但那样每次构建/发布都要你手工执行，我会失去"改完即验"的能力。

> 建议优先级：2 → 1 → 3。先试修复权限最省事；若 E: 不是 NTFS（外接盘常见 exFAT），2 不可行，直接走 1。

## 三、工作流提案

### 3.1 分支与提交（✅ 已确认 2026-09-05）

| 项 | 结论 |
|---|---|
| 权威远端 | **Gitee `saixiaofeng/football` 为唯一权威源**；GitHub `xushengzheng415-max/saixaifeng` 只作只读镜像，**不从本地推 GitHub** |
| 主干 | `main` 保存正式发布基线，不直接在 main 上开发；验收通过的改动从 `preview` 合进 main |
| 开发分支 | `main` + 长期 `preview` + 每任务一条短期功能分支；功能进入 main 后删除本地与远端分支 |
| 提交粒度 | 一个可独立验证的改动一次提交；提交信息带端别（PC / MP / FN / H5 / DOC） |
| 提交前自检 | `git diff --check`、`git status` 确认没有夹带对方的改动或临时文件 |
| 合并方式 | 各自从 main 拉取后再合并/变基，**禁止强推 main**；冲突当场解决，不带着冲突发布 |

### 3.2 分工边界（✅ 已确认：两人都是全栈，按任务切）

两人都做 PC + 小程序 + 服务号，因此**不按"人＝端"切，按"当次任务"切**。约定如下：

1. **发布前认领任务，写清"这次我改哪些端、哪些模块"**，避免同一文件被两人同时改。
2. **契约改动必须先在 `docs/ADR.md` 记一条**（改动日期 + 影响的端），再各自实现——这一条不变，因为 `webLoginApi` 的 action 和返回字段同时服务 PC / 小程序 / 服务号。
3. **共享文件单独约定**，不允许两人同时改：
   - `docs/CURRENT_STATUS.md`：**谁发布谁写**，插入位置固定为文件首行之后
   - `docs/AGENTS.md`、`docs/PRODUCT_RULES.md`、`docs/ADR.md`：改之前先跟对方说一句
4. **开发分支保持短命**：一个任务一条小分支，先进入长期 `preview` 验收；完整进入 `main` 且无人继续使用后，删除本地与远端功能分支。
5. **按端分文件天然减少冲突**：`web-admin-vue/`、`cloudfunctions/`、`miniprogram/`、`service-account-h5/` 各自独立，同时改不同端不会撞车；真正的高冲突只有上面第 3 条的共享文件。

### 3.3 发布协议（✅ 已确认：谁改谁发但先喊话）

1. **发布前喊话**：声明目标（`/admin/` / 云函数 / 小程序）和预计耗时，对方在这段时间内不发同一个目标。
2. PC 发布必须**全量构建 + 全量安全上传 + 上传后一致性校验**，禁止只补单个分包（否则 `index.html` 引用的哈希会 404）。
3. 云函数部署**先 `node --check`，再部署，再读回生产状态**（`AGENTS.md` 第五章）。
4. 发布后立刻把"构建入口哈希 / 分包哈希 / 无会话探针结果 / 云函数读回版本"写进 `CURRENT_STATUS.md`（谁发谁写）。
5. **任何生产写操作（部署、改配置、删数据）都需要当次任务的明确授权**，默认只读。

### 3.4 单工作副本的硬约束（⚠️ 技术限制，与分工无关）

R1 在本机是客观事实：**两人共用 `E:\Documents\sxf-football` 这一份工作副本**。因此：

- 一方 `git checkout` 切分支，会**直接改变另一方磁盘上的文件**；
- 一方生成的 `dist/` 会被另一方下一次构建覆盖；
- 未提交改动可能被 checkout 带走。

如果你们是**同一个 IDE 窗口 / 同一份工作区**，这两条开发分支在物理上就没法同时检出，只能"轮流切"。真正要用分支模型并行，两条路选一条（🔴 待你决定）：

- **A｜一人一份 clone**：第二个人再 clone 一份到别的目录（如 `E:\Documents\sxf-football-b`），各走各的分支与构建；
- **B｜`git worktree`**：在同一仓库下开两个 worktree 目录，共享 `.git`，但各自独立工作树。

> 注意：无论 A 还是 B，`sxf-cloud.ps1` 和构建命令的路径都要按各自目录来，别让两边的 `dist` 互相覆盖。

## 四、安全红线在双人场景下的补充

- **共享凭据只有一份**：平台管理员密码、`sxf-cloud` API Key 都在仓库外，不得因为两个人开发就复制出第二份明文。
- **测试账号不得变成业务判断条件**（`AGENTS.md` 3.3）：两人各自的调试账号不能写进代码分支逻辑。
- **数据库只读优先**：排查问题时先只读回读，确需写入的按"确认精确目标 + 单独验证"走。
- **不要为了跑通构建而关掉沙箱**：如果为绕过 ACL 直接给 `danger-full-access`，等于放弃文件写入边界，建议用第二节的方案 1/2 解决，而不是放权。
