# 球员卡套件统一规范

状态：2026-09-30 产品负责人确认的目标架构与验收口径。本文件不表示现有三端或生产环境已经完成改造。

## 一套配置、一套生成、各页调用

球员卡是独立的完整套件，不是某个页面的组件样式。平台后台统一管理模板、字段、坐标和素材；统一球员卡模块读取获授权的球员资料及已发布模板，生成完整成卡；手机、平板、PC 的列表、详情、阵容、分享和导出只调用模块返回的成卡，不在各页面排列人物、文字或卡面图层。

```text
平台后台配置并发布模板
  → 球员卡模块读取模板版本、球员资料和服务端等级
  → 同一渲染器生成成卡并保存版本
  → 各页面按球员 ID 与授权范围读取、缩放和展示
```

- 后台配置的是**字段映射和呈现规则**，不改球员事实。至少覆盖人物形象照、球衣号码、位置、姓名、球衣名、身高、体重、国旗、队徽；每项可配置显示、坐标、尺寸及适用的文字样式和层级。字段只从受控字段表选择，不接受任意数据库字段或页面自传的文字替换身份资料。
- 卡面底图、遮罩和前景、画布尺寸、人物裁剪区域、字段布局及字体由同一个模板版本管理。后台预览必须调用与正式成卡相同的渲染器，不能另做一张近似的 CSS 预览。
- 球员卡模块提供统一的制卡、更新、读取和状态接口。调用页只传稳定球员 ID、业务上下文及授权会话；返回成卡地址、模板 ID、已发布模板版本、卡片数据版本、等级与加载状态。各端可封装调用适配器，但不得再实现卡面绘制或等级算法。
- 同一已发布卡片在手机、平板和 PC 上保持相同画布比例、字段位置、人物裁剪、图层、文字和内容；**各端只等比缩放整张卡**。不能因屏幕宽度重新排版、裁切卡面、替换局部图片或另设字号。周边的操作按钮与页面布局可适配设备，但不得改变卡片内部。
- 没有成卡、正在生成、生成失败、无权读取须分别呈现。普通球员资料缩略图不能标作正式球员卡；缺失或失败不能默认铜卡、金卡或零分。

## 卡种、获得规则与展示选择

- 基础铜、银、金卡的当前获得规则统一使用 [球员卡积分与等级 v2](data-center/PLAYER_CARD_POINTS.md)：已核定比赛积分，加上每 10 滴有效球员应援蜂蜜折 1 分的应援积分，得到综合积分；0–44 铜、45–99 银、100 及以上金。没有正式出场的真实球员也可凭应援升级，综合满 100 分同样解锁已保存卡面换照与平台背景。卡片须显示比赛分、应援分和综合分的来源，不把蜂蜜写成出场、进球或赛事积分。
- 计入的蜂蜜须已从球迷账户扣除并送达稳定球员 ID，扣费与应援记录相互印证；签到余额、球队应援、测试数据及无法核实身份的旧记录不计分。该规则由统一服务端计分与授权，模板及调用页不能单独计算。当前套件架构仍处于实施阶段，现有页面接入状态以 [上线登记](data-center/RELEASE.md) 为准。

- 基础铜、银、金卡与限定卡属于同一球员卡套件中的不同卡种。后台以稳定 `cardTypeId` 管理卡种、名称、素材、字段布局、适用对象、发布状态与版本；生日卡、冠军卡、金球卡是未来可配置卡种的例子，**目前不预设它们的具体获得条件或上线状态**。
- 每种限定卡的获得规则单独登记规则 ID、版本、生效范围和时间、授权对象、数据来源、核验条件及发放/撤销策略。服务端从已确认事实判断资格并留下证据与审计记录；页面不能按生日字符串、赛事名称、奖项文案或客户端标记自行发卡。规则只能使用受控条件和参数；新增事实类型须先扩展套件的规则执行器与数据契约，不能在某个页面写一次性判断。
- 球员获得的限定卡与其基础等级卡**并存**，不会自动替换或改变铜银金等级。球员或依法有权的监护人可从已拥有且可展示的卡中选择当前展示卡；选择结果按稳定球员 ID 保存在服务端，所有端口读取同一选择。无权、未获得、已失效或被撤销的卡不能仅凭客户端传入的卡种 ID 显示为已拥有；回退到有效基础卡时须给出明确状态。
- 限定卡的获得及展示资格与基础卡积分、100 分换照片/背景权益分别校验，不能用限定卡外观冒充金卡，也不能把已有背景切换权益自动当作限定卡发放资格。若规则修订会影响已发卡，须明确是否追溯、保留或撤销，并记录处理结果，不静默清除球员已获得的卡。

## 后台发布与自动更新

- 草稿与已发布模板分离。发布产生不可变版本；保存草稿不影响正在使用的成卡。
- **后台发布新布局后，所有受影响的已保存成卡自动更新。** 这同时适用于基础卡和限定卡。球员卡模块使用保留的标准形象照、裁剪参数、当前获核定资料、基础等级与限定卡拥有记录，批量重生成对应卡种与模板的成卡。新制作的卡也使用同一新版本。
- 发布采用待激活版本：先完成重生成和校验，再统一切换活动版本。切换前各页面继续读取上一完整版本；失败的卡进入可追踪的质量队列，阻止本次版本整体激活，并向后台显示数量与原因。不得让同一模板的一部分页面显示新版、另一部分显示旧版，也不得跳过失败卡宣称全部更新。
- 每张成卡记录 `playerId`、`cardTypeId`、`templateId`、`publishedVersion`、`cardDataVersion`、`renderVersion`、文件 ID、生成状态与时间；限定卡另记录获得规则版本与证据引用。旧图片和版本保留供审计与回滚；成功激活后读取接口只返回当前活动版本。球员资料、标准形象照、已授予等级或有效卡种发生变化时，也由该模块触发重生成和缓存失效。
- 历史卡若缺少可重生成的源图、裁剪或稳定球员 ID，须先完成有记录的迁移或修复，再激活新模板；不能仅拿旧成卡截图二次绘制，也不能按姓名猜测身份。

## 数据、权限与验收

- 等级、积分及换照片或背景权益取统一服务端结果。测试比赛、测试球队、测试球员及来源不明数据不授予正式积分或等级；调用页不得按年龄、场次或卡面颜色推断。
- 本人、监护人、球队及公开页面分别按服务端权限读取。公开榜单字段不自动授权公开私有成卡；需要公开展示时须有明确的公开范围和成卡读取接口。
- 验收同一球员在手机、平板、PC 的列表、详情、阵容及导出显示同一活动模板版本和成卡内容，卡片内部只发生等比缩放；检查无卡、生成中、失败、无权、模板发布失败、旧卡迁移、资料修订、等级变化、限定卡发放/撤销、跨端展示选择和回滚。发布记录须有受影响卡数、成功数、失败数、活动版本及实际线上回读。

## 当前实现差距

PC 现有 `PlayerCard.vue` 固定部分布局，H5 和小程序有独立绘制入口；本地未部署的模板库原型只配置六类文字的位置与样式，球员端仍可保存静态成卡。它们不是已经完成的统一套件。后续实施须扩展后台字段配置、建立统一渲染和批量重生成服务、迁移历史卡、加入限定卡规则与拥有记录，并将各页面改为套件调用。生日卡、冠军卡、金球卡的具体获得条件仍待分别确认。知识库同步、Git 推送与后台模板保存均不等于这项改造已上线。
