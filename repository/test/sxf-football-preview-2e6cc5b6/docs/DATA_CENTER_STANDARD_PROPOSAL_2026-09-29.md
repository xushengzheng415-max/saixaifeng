# 赛小蜂足球数据中心统一方案

日期：2026-09-29。状态：用户已确认实施；正式知识库入口为 `docs/data-center/README.md`。当前实现、接入状态和发布边界分别见该目录 CONTRACT、INTEGRATION、RELEASE。

## 1. 目标和范围

让 H5、PC、小程序通过统一业务服务使用同一套权威数据；球队历史、球员生涯、球员为各队的贡献、赛事统计均可追溯到同一批比赛事实。新增功能必须明确数据来源、关联关系、计算口径、权限、完整度和受影响端。

本次检查范围是足球项目本地代码，未核查生产数据库全量内容，也未审计篮球项目。已有《赛小蜂赛事球队与球员标准化体系（足球篮球通用）》提供了长期身份、球队关系、赛事名单和比赛事件的概念基线，本方案补充统计归属、接口契约、规模化查询和迁移验收。未来跨运动项目可共用身份模型，但足球与篮球指标分别定义，不混合累计。

第一阶段沿用现有 CloudBase 和管理后台，通过公共业务模块逐步收拢读写与统计。统一服务可以包含多个业务接口、云函数和数据集合，不要求所有代码集中到一个巨大函数。按实际查询规模再决定缓存、任务队列及分析存储的引入。

## 2. 数据归属：事实记录一次，按不同范围汇总

球队成绩与当前队内球员的生涯成绩是两种数据，不能相互替代。

| 查询范围 | 含义 | 归属依据 |
|---|---|---|
| 球员生涯 | 同一球员在平台有记录且满足统计条件的全部比赛 | 稳定球员身份 |
| 球员为某队贡献 | 球员代表指定球队产生的比赛表现 | 比赛当时的球员与球队关系 |
| 球队历史 | 球队历届赛事中的成绩与球队指标 | 比赛当时的参赛球队身份 |
| 球员单届赛事 | 球员在指定赛事、组别中的表现；可进一步按代表球队筛选 | 赛事、组别、球员及参赛关系 |
| 球队单届赛事 | 指定球队在该赛事、组别中的成绩 | 赛事、组别及参赛球队关系 |
| 赛事整体 | 该赛事各组别、球队、球员的结果与榜单 | 赛事范围和规则版本 |
| 平台整体 | 平台内去重后的比赛、球队、球员及按项目统计的汇总 | 稳定身份、比赛唯一标识及明确覆盖范围 |

示例：小明代表 A 队在甲赛事进 5 球，转会后代表 B 队在乙赛事进 3 球。小明生涯为 8 球；为 A 队贡献 5 球，为 B 队贡献 3 球；A 队原有贡献保留，B 队不会获得转会前的 5 球；甲赛事仍记录小明当时代表 A 队。

如果 A 队当前所有球员的生涯进球相加为 100 球，这个数字只能称为“当前阵容球员生涯累计”，不能称为“A 队历史进球”。球队进球还可能包含乌龙球和未关联正式球员的进球，与本队球员进球之和不必相等。

平台统计只代表平台可追溯数据。外部赛事导入需要单独标记来源、验证状态和覆盖范围，不能直接声称覆盖球员现实中的全部生涯。

## 3. 最小数据模型

以下是目标概念模型，集合名称与实际迁移映射在实施时确定，不表示当前数据库已经具备这些实体。

| 实体 | 核心关联 | 职责 |
|---|---|---|
| 球员主档案 | playerId | 永久身份、基础资料、验证状态；不把生涯绑定在当前球队上 |
| 球队主档案 | teamId、organizationId | 长期球队身份、组织归属、名称与队徽；更名不重建身份 |
| 球队球员关系 | membershipId、playerId、teamId、有效起止时间 | 任职、加入、离队、转会历史；兼容被允许的多队关系 |
| 赛事与组别 | tournamentId、divisionId、sportType、ruleVersion | 赛事范围、比赛规则、排名和纪律口径 |
| 球队参赛关系 | registrationId、tournamentId、divisionId、teamId | 球队参加某届某组别的资格和状态 |
| 球员参赛关系 | entryId、registrationId、playerId | 球员当届代表球队、号码与资格；允许性由赛事规则决定 |
| 审核名单快照 | rosterSnapshotId、registrationId、version | 保存当时审核通过的名单及必要展示资料 |
| 比赛 | matchId、tournamentId、divisionId、主客参赛关系 | 比赛对象、阶段、时间、结果与审核版本 |
| 单场阵容与上场记录 | matchId、entryId、playerId、teamId、名单版本 | 区分报名、替补入名单、实际出场和上下场时间 |
| 比赛事件 | eventId、matchId、事件类型、关联参与者、revision | 进球、助攻、牌、换人等事实和修订 |
| 官方结果记录 | matchId、resultVersion、状态、审核信息 | 正式比分、判罚结果、弃权等不能只靠事件推导的结果 |
| 身份映射与修订记录 | 原系统、原记录ID、目标ID、操作人与原因 | 历史兼容、导入去重、身份合并和追溯 |
| 统计汇总 | 对象ID、统计范围、规则版本、数据版本 | 可重算的查询结果，不能作为唯一事实来源 |

事件字段按事件类型定义必填项。比赛和球队是比赛事件的基本范围，球员相关事件需要正式身份或明确的“待关联”状态。换人须分开记录换入和换出球员；助攻须明确助攻者；乌龙球须区分事件所属球队、进球受益球队和球员当时代表球队。

球队层级须区分俱乐部/机构与实际参赛队伍，例如俱乐部 U10、U12 不是同一个参赛队。按机构汇总应使用上级组织关系；球队赛季变化、更名与拆分需要连续性规则和人工确认，不能仅按名称合并。

## 4. 转会和历史身份规则

1. 转会结束旧球队关系并创建新关系，球员 playerId 保持不变；不得把已有比赛的 teamId 批量替换成新球队。
2. 查询历史以当时审核名单、参赛关系、单场阵容和事件为准，不能以当前球员库反推历史。
3. 球衣号码、比赛位置、赛事资格属于球队/赛事/比赛关系，不作为球员永久身份。
4. 赛中转会、借调、同时代表多队，由赛事资格规则决定；历史归属仍以实际批准的参赛记录为准。
5. 姓名、手机号、球衣号码都不能单独用于自动合并球员。历史模糊记录进入待确认队列，未确认前不得写入正式个人累计。
6. 身份合并保留原 ID 映射和证据，重算受影响统计；球队身份合并同样需要审核与回滚依据。
7. 历史成绩保留，不代表新球队获得原队的家长联系方式、身份材料或其他私密信息。球员对自身历史的访问和组织访问权限分别校验。
8. 黄红牌历史表现可以按范围汇总；停赛和资格处罚的执行范围由纪律规则决定，不能简单继承全部赛事的处罚。

## 5. 统计指标字典

每个指标必须在受版本管理的字典中登记：标识、中文名、单位、适用项目、统计粒度、来源、计算公式、比赛状态、去重规则、缺失处理、权限、规则版本和负责人。前端禁止自行创造另一套计算公式。

| 指标示例 | 统一要求 |
|---|---|
| 球员出场 | 实际上场的不同 matchId 数；报名或坐替补席不算出场 |
| 球员进球 | 有效球员进球事件；乌龙球、点球大战按规则分开，不默认混入 |
| 助攻 | 明确有效助攻关联；同一进球的关联助攻与独立助攻事件不得重复计数 |
| 出场时间 | 有完整计时和上下场依据才计算；缺依据显示未知或已知部分及覆盖率 |
| 球队胜平负 | 使用审核后的官方结果；弃权、改判和点球决胜按赛事规则处理 |
| 球队进失球 | 使用对应范围的官方比分规则；与球员明细差异进入对账，不强行补到某个球员 |
| 赛事积分排名 | 按赛事/组别规则版本计算，不把不同赛事积分直接加成平台排名 |
| 平台场次数 | 按唯一 matchId 去重；一场比赛不能因两队各有记录而计两场 |
| 平均、比例指标 | 汇总分子分母后计算，不能直接累加或平均各赛事的百分比 |
| 奖项与荣誉 | 保留正式授予记录和赛事来源，不能仅根据当前榜单反推历史奖项 |

正式累计默认使用审核通过的有效结果；现场数据单独提供实时/暂定口径。具体旧状态到新状态的映射先清点，再在适配层固定，不能由各页面自行判断 completed、finished、archived 等状态。

赛事榜单、个人生涯和平台榜单使用相同指标定义，但统计范围与适用规则不同。跨年龄组、赛制和比赛时长的总量需要明确筛选条件，不直接解释成能力排名。

## 6. 缺失、质量和数据包范围

零、未知、部分记录、未采集、不适用、无权限、查询失败必须区分。尤其不能把读取失败或未录入的射门、助攻显示成 0。

统计响应同时返回字段完整度和范围完整度。建议状态：complete、partial、not_collected、unavailable、not_applicable；访问无权限通过权限错误或字段授权状态表达。还应返回 expectedMatches、coveredMatches、unlinkedEventCount、pendingReviewCount、更新时间、数据版本。

数据完整度按指标计算：比分完整不代表助攻完整，进球完整不代表出场时间完整。混合部分完整与部分缺失的比赛，累计必须标明覆盖范围。

简易版手工姓名事件保留原始记录，可以参与符合条件的球队统计，但未核实身份前不计入正式球员生涯。补关联经审核后更新原事件关联或修订版本，不能再创建一个重复进球。

当前赛事流程免费，数据采集和访问遵守业务权限，不设置专业版或数据包付费开通门槛。统计服务按实际采集覆盖率输出结果，历史未采集的个人指标不能伪造补齐；后续新增收费能力另行确认，不得由统计代码随意抹除事实。

## 7. 写入、修订与汇总流程

业务提交 → 校验身份/权限/赛事范围 → 幂等写入事实 → 审核或归档 → 更新相关统计 → 发布同一数据版本 → 各端读取。

- 重试、重复导入和离线补传使用业务幂等键；同一动作不得因网络重试重复计数。
- 事件修改、撤销、身份补关联和官方结果改判保留版本、原因及操作人；统计只采用有效版本。
- 修改一场比赛时，需要更新该场明细、相关球员生涯、球员球队贡献、球队累计、赛事榜单和平台汇总。
- 汇总更新失败可重试，事实与待处理任务须可靠关联；补充周期对账，防止触发任务丢失造成长期漏算。
- 重算构建新的完整版本，校验通过后发布；中途失败不把部分完成的结果当作完整版本返回。
- 单场最终比分与事件对账，差异形成有原因的异常。改判、弃权、乌龙及无球员关联可产生合理差异。

预先生成可重建的统计汇总，可减少各端重复扫描大批历史数据。汇总必须从权威事实生成，变化后更新，同时暴露刷新时间与版本。这遵循 [Microsoft 的 Materialized View 设计说明](https://learn.microsoft.com/en-us/azure/architecture/patterns/materialized-view)，此处不要求引入 Azure 服务或把整个系统改成事件溯源架构。

## 8. 统一接口契约

以下是业务能力建议，HTTP 路径或云函数 action 在实施时按当前路由约定确定。

| 能力 | 必要范围 | 返回内容 |
|---|---|---|
| 球员档案与生涯 | playerId、sportType、时间/赛季、统计模式 | 档案、历次球队关系、指标、覆盖率 |
| 球员球队贡献 | playerId、teamId、时间/赛季 | 历史效力区间、相关比赛与贡献 |
| 球队历史 | teamId、sportType、时间/赛季 | 历届参赛、成绩、现役与历史贡献分别展示 |
| 球队赛事数据 | registrationId 或赛事+组别+teamId | 正式名单、比赛、该届球队指标 |
| 球员赛事数据 | entryId 或赛事+组别+playerId，可加 teamId | 当届身份、球队归属、比赛与指标 |
| 赛事榜单 | tournamentId、divisionId、指标、规则版本 | 有效排名、统计覆盖和数据版本 |
| 平台汇总 | 项目、时间/赛季、地区等授权筛选 | 去重总量、清晰范围及规则 |
| 比赛事实与修订 | matchId、角色权限、预期修订版本 | 事实、审核状态、冲突提示 |

统一要求：

- 使用固定的响应结构、字段类型、时间格式、单位和错误码；时间存储使用统一时间标准，展示按明确时区。
- 响应包含 schemaVersion、metricVersion、dataVersion、generatedAt、scope、coverage 和来源追溯信息。
- 列表使用稳定排序和游标分页，明确 hasMore/nextCursor；超过处理上限返回“不完整”或转后台任务，不静默截断。
- 球员与球队列表不携带全部生涯事件，明细、汇总和导出分别查询；字段按权限最小化返回。
- 组织隔离由服务端结合访问者与业务对象校验，不能仅相信请求传入的 organizationId。
- H5、PC、小程序共用同一契约，各端只处理展示；公开接口、组织管理接口和本人接口采用各自授权范围。
- 导出与页面使用同一统计服务和版本；外部互联使用稳定 ID、契约版本、来源 ID、幂等键和授权范围。

## 9. 规模化读取与运行保障

1. 按真实查询组合建立索引，例如赛事+组别+比赛、球队+发生时间、球员+发生时间；索引要结合 CloudBase 实际限制和执行情况验证。
2. 当前名单与长期历史查询分离，历史查询不能只从当前球员列表出发，否则已离队球员会消失。
3. 高频查询读取统一汇总；事实写入、近实时更新、归档更新和全量重算使用适合各自场景的执行路径。
4. 大导出和跨平台重算拆成可恢复批次，记录游标、完成范围与失败原因，不依赖一次请求扫描全库。
5. 监测统计更新延迟、事件未关联数、读取失败数、对账差异、任务积压和分页完整性。
6. 公共榜单缓存与组织/本人私有数据分开，缓存键必须包含统计范围、规则版本及必要授权边界。
7. 历史归档不能破坏赛事追溯；身份资料脱敏、删除要求传播到查询和派生结果，具体保留政策另行确定。
8. 暂不承诺具体容量或实时 SLA；先采集比赛数、事件量、并发、查询耗时和任务成本，再确定性能目标与升级阈值。

## 10. 数据中心后台的最小职责

放入现有 PC 后台，不重复建设另一套日常球队/赛事管理页面。重点提供：

- 身份和来源查询：找到球队、球员、历史 ID 映射与记录来源。
- 关系查询：当前/历史所属球队、参赛关系、赛事和比赛名单。
- 数据质量队列：重复身份、未关联事件、缺失参赛关系、比分差异、统计覆盖不足。
- 修订和重算：先显示影响的比赛/球队/球员/赛事，再执行经权限控制的修订或统计重算。
- 运行状态：数据版本、更新时间、失败任务、修订审计和完整度。

后台修订使用业务接口，不开放任意数据库编辑来绕过规则。是否允许身份合并、统计纠错等高权限操作，需在角色权限规范中明确。

| cloudfunctions/getMiniWorkspace/officialRosterStats.mjs | 已区分替补名单和出场；缺少可靠计时保持未知；存在历史姓名适配 | 可复用规则，但需形成统一字典和身份确认策略，区分正式结果与历史推断 |

不能据此断言所有历史数据已缺失，也不能认为已有设计文档中的实体已全部实现。需通过集合盘点、关系覆盖率、分页计数与事实对账建立证据。

## 12. 实施阶段与验收

### 阶段一：规范与盘点

产出字段字典、实体关系、指标字典、状态映射、接口契约、现有调用清单和数据质量基线。每个规范字段标明当前对应集合/字段、已实现/部分实现/未实现及维护责任。

优先盘点身份复用、teamId/teamCode、赛事/组别范围、事件来源、审核状态及查询上限；旧文档与现行代码有差异时登记差异，不擅自以文档替代事实。

### 阶段二：统一读取与完整度

先统一球队赛事数据、球员赛事数据、名单/阵容和事件读取，补分页、统计覆盖、版本和权限。H5、PC、小程序用相同条件验证返回值一致；旧接口保留适配，不一次切断。

### 阶段三：稳定身份与长期统计

建立可审核的身份映射和带起止时间的球队关系，补个人生涯与球队历史服务。历史模糊记录先标记，不靠同名强行合并。修订、转会、撤销与重算形成完整链路。

### 阶段四：后台与规模保障

实现质量队列、修订审计、受控重算和失败重试；按实际负载增加索引与汇总。先用代表性赛事和隔离数据验证，再确定迁移批次、备份与回滚方案，经上线授权后执行。

### 必须通过的业务验收

1. 球员转会后生涯累计保持连续，原球队贡献不减少，新球队不获得旧贡献。
2. 球队更名、球员离队或当前档案变化，不改变历史赛事当时的参赛归属。
3. 同名球员、同号球员、跨组织账户不会自动合并或串数据。
4. 一场事件修订后，个人、球队、赛事和平台相关统计更新到一致版本；重试不重复计数。
5. 报名未上场、替补未上场、乌龙球、点球大战、弃权和改判按字典正确处理。
6. 正式与实时统计分开；停赛资格按适用赛事纪律规则执行。
7. 查询数据超过 200、1000 等历史限制后仍能完整处理；超过任务上限有明确状态和可恢复进度。
8. 数据缺失、未采集、无权限与读取失败不显示成正式零值；指标覆盖率正确。
9. H5、PC、小程序、导出在相同范围和数据版本下结果一致。
10. 同场比赛的平台场次数只计一次；总量、比例、积分排名按各自规则汇总。
11. 手工事件身份补关联后无重复事件和重复统计；历史身份合并可追溯。
12. 数据包覆盖与访问权限符合统一政策，转会不泄露原队私密信息。

## 13. 防遗漏的研发交付门槛

每项新增数据功能必须交付以下内容，作为评审和验收依据：

- 业务范围：对象、赛事、组别、项目、时间及正式/实时模式。
- 来源清单：权威事实、旧字段兼容、缺失与失败策略。
- 指标规范：公式、单位、版本、去重及特殊事件规则。
- 接口变更：契约、分页、权限、兼容期及受影响端。
- 更新传播：哪些统计随写入、修订、撤销和身份合并重算。
- 数据质量：覆盖率、对账方式及异常处理入口。
- 业务验收：至少覆盖本功能涉及的跨端、转会、历史归属、缺失、重复和大数据量场景。

这些内容应纳入仓库规范、接口校验和持续检查；文档要与代码同版本维护。后台负责发现和处理异常，持续一致性由统一规则、业务服务与验收保障。
