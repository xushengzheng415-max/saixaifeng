# 赛小蜂足球分阶段整改执行计划

更新时间：2026-07-05

目标：在不打乱现有可用功能的前提下，把赛小蜂足球从“多端、多角色、多历史功能混杂”的状态，逐步整理成“青少年足球赛事 + 小程序优先 + 主办方 PC 管理 + 赛事中心展示”的清晰产品结构。

## 一、当前判断

目前已具备的基础：

- 各端报名主流程基本可用。
- 球队端基础管理基本可用。
- 小程序已有球队、球员、赛事、报名、阵容、裁判、赛事中心等页面基础。
- Web 管理后台已有赛事、球队、球员、裁判、抽签、赛程等基础页面。

当前主要风险：

- 功能是散的，还没有完全串起来。
- 分享链接创建球队、分享链接创建球员还没有确认跑通。
- UI 系统需要整体统一。
- 历史遗留的多余端口、多余页面、多余功能还没有清理。
- 原型和代码当前不完全一致，容易边改边乱。

## 二、执行总原则

1. 一步一分支，一步一验收。
2. 每一步只解决一类问题，不混着改。
3. 先验证现有闭环，再删功能。
4. 删除前先标记，标记后再迁移，迁移后再删除。
5. UI 系统先建规则，再批量替换页面。
6. 小程序优先保证用户链路，PC 只保留主办方和赛事中心管理。
7. 每个阶段都同步 GitHub Issue/PR，分支也要通知到位。

## 三、目标产品结构

### 保留端口

| 端口 | 保留原因 | 主要功能 |
| --- | --- | --- |
| 小程序 | 所有现场和日常用户入口 | 球队、球员/家长、裁判、报名、阵容、赛事中心展示 |
| 主办方 PC | 复杂管理工作台 | 创建赛事、报名审核、抽签分组、赛程管理、裁判管理、数据统计 |
| 赛事中心 PC | 内容和展示管理 | 赛事发布、展示配置、Banner、专题、公开数据维护 |

### 取消或弱化端口

| 端口 | 处理方式 | 原因 |
| --- | --- | --- |
| 球队 PC | 取消 | 球队负责人通过小程序分享链接给球员/家长自填资料，不需要 PC 管理台 |
| 普通裁判 PC | 取消或弱化 | 裁判现场执法更适合小程序/平板横屏 |
| 大屏配置独立菜单 | 取消 | 抽签大屏归入抽签分组，不作为主办方侧边栏一级菜单 |

## 四、阶段 0：冻结基线和建立看板

目标：先把当前状态定住，避免边删边乱。

任务：

1. 建立 GitHub Issue：`赛小蜂足球整改总计划`
2. 建立子 Issue：
   - 分享链接闭环测试
   - 小程序端口清理
   - 主办方 PC 侧边栏调整
   - 球队 PC 取消
   - 裁判端链路整理
   - UI 系统统一
   - 赛事中心展示端整理
3. 建立主分支策略：
   - `codex/football-roadmap-baseline`
   - 后续每个阶段单独分支
4. 记录当前可用功能：
   - 报名
   - 球队端
   - 赛事详情
   - 参赛名单
   - 裁判入口
   - 赛事中心入口

验收标准：

- 总计划文档确认。
- GitHub Issue/PR 规则确认。
- 当前可用功能清单确认。
- 不做任何删除。

## 五、阶段 1：分享链接闭环优先跑通

目标：先确认最关键的球队增长链路跑通。

### 1.1 分享链接创建球队

要验证的流程：

1. 主办方或已有用户生成创建球队链接。
2. 微信内打开链接。
3. 新用户登录/授权。
4. 填写球队资料。
5. 成功创建球队。
6. 创建人自动成为领队/管理员。
7. 球队出现在球队列表和赛事报名流程中。

检查点：

- scene 参数解析是否正确。
- 邀请码是否过期。
- 登录后是否能回到原目标页。
- 手机号、openId、unionId 绑定是否正确。
- 重复点击是否会创建重复球队。

### 1.2 分享链接创建球员

要验证的流程：

1. 球队负责人生成球员建档链接。
2. 分享到微信群。
3. 球员/家长打开链接。
4. 登录/授权。
5. 填写球员资料。
6. 上传头像/证件照。
7. 提交后自动归属球队。
8. 球队负责人能看到资料状态。

检查点：

- 邀请链接是否携带 teamId。
- 球员资料是否正确绑定 teamId。
- 家长手机号和球员身份是否区分。
- 已提交、待完善、已确认状态是否清晰。
- 重复提交是否会覆盖或生成重复球员。

验收标准：

- 两条分享链路都能真实跑通。
- 失败场景有提示。
- 关键数据能落库。
- 小程序 WXML 不引入复杂表达式。

## 六、阶段 2：小程序端口和页面清理

目标：先清理小程序入口，不直接删代码。

任务：

1. 对 `app.json` 注册页面做一张表：
   - 正式保留
   - 待合并
   - 待迁移
   - 待删除
2. 对未注册页面做一张表：
   - 有价值但未注册
   - 历史旧页面
   - 可删除页面
3. 明确四个正式小程序身份入口：
   - 主办方
   - 球队/教练
   - 裁判
   - 球员/家长
   - 赛事中心展示
4. 清理重复页面命名：
   - 例如 `pages/team/player-add`
   - 例如 `pages/team/player-add/player-add`
   - 先确认哪个是正式页，再迁移入口。

执行方式：

- 第一步只加标记文档，不删。
- 第二步改入口。
- 第三步验证入口。
- 第四步再删除废弃页面。

验收标准：

- 小程序每个 Tab 和跳转入口都能解释清楚。
- 没有“看起来有页面但进不去”的核心功能。
- 删除页面前有替代路径。

## 七、阶段 3：主办方 PC 收口

目标：主办方 PC 只保留赛事管理需要的复杂能力。

侧边栏目标：

1. 工作台
2. 我的赛事
3. 创建赛事
4. 报名审核
5. 抽签分组
6. 赛程管理
7. 裁判管理
8. 数据统计
9. 设置

明确删除：

- 独立“大屏配置”

处理方式：

- 抽签大屏入口放入“抽签分组”。
- 抽签分组内补：
  - 预览抽签大屏
  - 发布到大屏
  - 复制播放链接
  - 下载二维码

验收标准：

- 主办方 PC 菜单不出现球队 PC 管理思路。
- 不出现独立大屏配置一级菜单。
- 抽签大屏能力能从抽签分组进入。

## 八、阶段 4：取消球队 PC，强化小程序球队链路

目标：把球队端从 PC 管理思路切换到“小程序 + 分享链接自填”。

任务：

1. 原型取消球队 PC。
2. 代码层面隐藏或移除球队 PC 独立入口。
3. 小程序球队首页强化：
   - 创建球队
   - 邀请球员自填资料
   - 球员资料完成状态
   - 一键提醒未完善球员
   - 报名赛事
   - 提交阵容
4. 球员资料页补齐青少年字段：
   - 年龄组
   - 身高
   - 体重
   - 学校
   - 监护人
   - 监护人电话
   - 证件照

验收标准：

- 球队负责人不依赖 PC 也能完成建队、收集资料、报名、提交阵容。
- 球员/家长能通过微信链接自填。
- PC 中没有球队端独立后台入口。

## 九、阶段 5：裁判端串联

目标：裁判端从“页面存在”变成“比赛链路可用”。

优先顺序：

1. 我的执法
2. 比赛详情
3. 首发名单确认
4. 比赛执法
5. 赛果提交
6. 赛后报告

普通裁判：

- 使用小程序/平板横屏。
- 不做普通裁判 PC。

裁判长/管理员：

- PC 保留轻量管理能力：
  - 裁判分配
  - 执法记录
  - 赛果复核

验收标准：

- 裁判能看到自己的比赛。
- 能确认双方首发。
- 能记录进球、黄牌、红牌、换人。
- 能提交赛果。
- 管理员能复核。

## 十、阶段 6：赛事中心展示端整理

目标：赛事中心只做公开展示，不混入管理。

小程序赛事中心应包含：

- 赛事列表
- 今日赛程
- 最新赛果
- 积分榜
- 射手榜
- 参赛球队
- 赛事详情
- 赛事规程

Web portal 应收口为：

- 青少年足球赛事展示
- 赛事列表
- 赛事详情
- 赛程
- 榜单
- 球队
- 比赛结果

验收标准：

- 游客/家长/球员进入赛事中心不会看到管理功能。
- 主办方管理功能回到主办方 PC。
- 教练报名功能回到球队小程序链路。

## 十一、阶段 7：UI 系统整改

目标：先统一设计系统，再逐页改 UI。

### 7.1 设计 Token

需要统一：

- 主色：绿色体系
- 辅色：青少年活力色，但不做杂乱彩虹
- 字体层级
- 圆角
- 阴影
- 按钮高度
- 表单间距
- 卡片样式
- 状态标签
- 空状态
- 默认头像
- 默认队徽

### 7.2 小程序 UI 组件优先级

优先统一：

1. 页面头部
2. 身份卡片
3. 赛事卡片
4. 球队卡片
5. 球员卡片
6. 表单
7. 底部操作栏
8. 状态标签
9. 空状态

### 7.3 Web UI 优先级

优先统一：

1. 主办方侧边栏
2. 顶部栏
3. 表格
4. 筛选区
5. 表单页
6. 详情页
7. 审核页
8. 抽签分组页

验收标准：

- 不再每个页面一套风格。
- 青少年足球品牌识别统一。
- 赛小蜂足球 LOGO 使用一致。
- 旧成人赛事分类视觉移除。

## 十二、阶段 8：删功能和删端口

目标：最后再删，不提前删。

删除顺序：

1. 删除入口
2. 验证无跳转依赖
3. 标记代码废弃
4. 保留一个版本观察
5. 删除代码
6. 跑构建和小程序检查

优先删除：

- 球队 PC 入口
- 成人赛事分类入口
- 旧版重复小程序页面
- 未注册且无价值页面
- 独立大屏配置入口

验收标准：

- 删除后没有 404。
- 删除后没有编译错误。
- 删除后主流程不受影响。
- 删除记录写入 PR。

## 十三、每一步的固定工作流

每个阶段都按这个流程走：

1. 建 Issue
2. 建分支
3. 写本阶段目标
4. 做最小改动
5. 本地验证
6. 更新文档
7. 提 PR
8. 在 PR 里写：
   - 改了什么
   - 删除了什么
   - 没动什么
   - 怎么验证
   - 下一步是什么
9. 合并后再开始下一阶段

## 十四、建议第一批执行顺序

第一批只做 4 件事：

1. 分享链接创建球队跑通
2. 分享链接创建球员跑通
3. 小程序页面入口清单确认
4. 主办方 PC 侧边栏去掉独立“大屏配置”规划

第一批不做：

- 不大规模删页面
- 不整体重做 UI
- 不重写裁判链路
- 不动数据库结构大迁移

## 十五、第一批验收清单

| 验收项 | 通过标准 |
| --- | --- |
| 分享创建球队 | 微信链接进入后能完成建队并绑定创建人 |
| 分享创建球员 | 微信链接进入后能提交资料并归属球队 |
| 资料状态 | 球队负责人能看到已完成/待完善 |
| 小程序入口 | app.json 页面用途清楚，无核心功能不可达 |
| 主办方 PC 菜单 | 规划中不再出现独立大屏配置 |
| 删除策略 | 有待删清单，但暂不直接删 |

## 十六、当前结论

先不要急着重构所有端。第一步应该把“分享链接建队/建球员”跑通，因为它决定球队端是否可以彻底脱离 PC。只要这条链路跑通，球队 PC 就可以放心取消，后续 UI 和删功能才不会乱。
